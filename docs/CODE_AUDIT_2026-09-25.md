## 0. 一句话结论

**正常路径没有 bug——问题全部集中在"边界条件 + 异步时序"上，其中最贵的一条是模型进程的错误处理策略：任何一次 Python 级异常（多半来自坏输入或磁盘满）都会让整个模型进程退出，下一个请求要付"重新拉起进程 + 重新加载模型 ≈ 12–14s"，而这段代码本来是可以只报错不重生的。** 其次是 GPU 探针在并发轮询下的放大效应（一次 nvidia-smi 卡住 → 每个标签页每 0.5s 各起一个子进程 → anyio 线程池被吃光 → 资源条冻结）。两类都修了。

审查中还确认了一件让人意外的事：**这条 Web 路径完全没有任何参考音频特征缓存**（`grep cache` 只有显存释放和 GPU 快照）。同一音色反复生成时，参考音频的编码每次重付——见 §4 的 O1，它现在是这份报告里性价比最高的一条。

## 3. 刻意保留的取舍（不是 bug，但要知道）

1. **`--stop` 的孤儿识别是启发式**（`run.py:273-285`：命令行含 `multiprocessing` + `spawn_main` 且父进程已消失）。想收紧成"只杀本项目的 worker"做不到——spawn 子进程的命令行里**不带项目路径**，它只有 `-c from multiprocessing.spawn import spawn_main ... --multiprocessing-fork`。理论依据：任何 Python 多进程程序在父进程先死时都会被误伤。缓解是 L3 的打印命令行 + 这里是显式清理命令。彻底解法见 O8。
2. **`reload=False`**（`run.py:373`）。改后端必须重启才生效——这是刻意的：uvicorn 的 reloader 会带着模型子进程一起重生，8GB 卡上等于随机多付一次加载。启动器已经用 `code_mtime` 在替换旧实例时提示"原实例跑的是被改之前的代码"。
3. **`outputs/` 没有自动清理**（`uploads/` 有 7 天 TTL，`app.py:52-79`）。生成结果删不删是用户的决定，页面里有删除入口；自动扫走用户想留的音频更糟。
4. **参考音频超 30s 直接拒绝，不自动截断**（`app.py:_measure_reference`）。官方训练预算就是 30s（参考与目标共用同一条序列），自动截一段是替用户做他没同意的决定；现在给的是"请在页面上截取其中一段（5–8s 最佳）"。
5. **全常驻不做硬性预检拒绝**，只把状态标成 ⚠ 警告（`app.py:1262` 门槛 14GB；真正放不下时由 503 兜底）。12GB 显存的卡属于"能塞下但很紧"，替用户判死不如给读数。

## 4. 优化与改进建议（未实施）

约定：**资源类建议必须真的降低绝对需求，并给出最低配置结论和逐条代价**；只缓解症状的一律不写。凡未在这台机器上实测的数字都标「需实测」。

### 4.1 性能与显存

**O1 · 参考音频特征缓存（按内容 md5 做键）— 本报告里最值得做的一条**
- 现状：`app.py` / `infer_auk.py` 里没有任何参考特征缓存（`grep` 结果只有显存释放）。每次生成都重跑参考音频的 VAE latent + Qwen 音频 token。
- 证据：`worker.log` 实测同一次请求内**第 1 段 15.9s、第 2 段 4.8s**（目标各 2.5s/2.0s）。这 11s 的差是首轮固定成本，里面既有参考编码也有首次分页搬运——**所以第一步是先拆剖面（O2），别照这个差值做预算**。
- 做法：上传落盘时就用内容 md5 命名（现在是 `uuid4().hex`，`app.py:1284`），worker 侧以 md5 缓存 `(latent, audio_tokens)`，LRU 上限 4–6 条（一条 latent + token 序列按 30s 算体积很小，需实测）。命中条件必须同时要求"模型实例未重建、显存策略未变"。
- 收益（待实测的区间）：同音色反复试听时省掉一次参考编码；对分页卡还顺带省掉参考那一路的换页。
- 代价：① 缓存吃常驻显存/内存，8GB 卡上必须在卸载模型时一并清空（顺序：先清特征引用 → `gc.collect()` → `empty_cache()`）；② 内容 md5 相同但显存策略不同时必须失效，写错就是**静默用错音色**；③ 多几 GB 常驻会抬高 §4.1 O5 说的提交内存峰值。
- 最低配置结论：8GB 显存 / 31GB 内存的机器上可以做（缓存的是小体量 latent），16GB 内存机器要先解决 O5。

**O2 · 分阶段计时剖面脚本（做 O1 的前置）**
- 做法：`scripts/` 下加一个脚本，固定 2–3 个用例（短/中/长 + 同一参考），逐阶段打点：参考读取 → VAE → Qwen token → DiT 每步 → 声码 → 落盘，并分别记耗时与显存峰值（耗时和峰值分开测）。
- 收益：这是这份报告里唯一能把「需实测」变成数字的工具；后面每一项（含 O1、O3）都要和它比。
- 代价：一次性投入（约几十行 worker 侧插桩 + 一个不进依赖的安装即用的 runner）。**优先级最高**，因为它让其它建议变成可判定的。

**O3 · 编码器再降一档精度（7.5GB Qwen 编码 → int8/fp8）**
- 现状：分页策略下权重 bf16 合计 12.8GB（`app.py:1259`），其中 Qwen 约 8.1GB。
- 做法：只对编码器做 per-tensor int8（或 fp8），输出转回 float 参与后续 fp32 归一化。
- 收益（需实测）：**真的降低绝对需求**——分页卡上搬运量近似减半，加载峰值也下来；这是唯一能把全常驻门槛往 8GB 方向拉的路线。
- 代价：① 音色/情感跟随有偏移风险，**必须同文本同参考做 A/B 试听**才算通过；② Windows 上没有现成的 kernel 收益，速度增益不要指望，主要是省；③ 量化实现要动 `infer_auk.py`，与本报告的"不改契约"原则不冲突，但和官方 checkpoint 的数值一致性会丢，需要留一条 `AUK_QUANT=0` 关掉的路。
- 最低配置结论：8GB 卡即使量化也**放不下全常驻**（12.8→约 7GB 再叠 context 与激活），所以它的意义是让"分页"更快、加载峰值更低，不是把 8GB 变成全常驻可用。别用它给用户这个预期。

**O4 · worker 预热（服务启动时把 torch 的导入成本先付掉）**
- 现状：模型进程是 `spawn` 出来的，首次 `_ensure_process` 要付解释器启动 + 导入 torch/transformers（实测模型加载本身 12.6–13.9s，导入是其中一部分）。
- 做法：`/api/health` 里加"预热"开关，或页面「加载模型」旁边给"预启动模型进程"（只 import、不加载权重）。
- 收益：把首次请求的一部分固定成本挪到用户还在点按钮的时候。
- 代价：**抬高常驻内存地板**——这正是 16GB 机器跑不动的根因（见 O5）。所以它必须做成默认关闭的开关，不能变成自动行为。
- 最低配置结论：31GB 内存的机器可以开；16GB 内存的机器**不要开**。

**O5 · 加载峰值（实测提交内存峰 25GB）压下来的三条路，以及 16GB 机器的结论**
- 现状：常驻 ~17.6GB，生成峰 25.8GB，加载峰 38.5GB（提交内存口径）。Windows 上超额分配不报错，直到 WinError 1455。
- 路 A（改法在权重侧）= O3 量化，绝对需求真的降。
- 路 B（改法在读取侧）：加载时分块 `safetensors` → 直接搬到设备，避免"整份 CPU 张量 + 设备副本"同时存在；收益是加载峰，代价是要动 `infer_auk.py` 的加载函数并验证与官方权重逐字节一致（**验收契约：同 seed 输出必须逐字节一致**，否则视为改坏）。
- 路 C（不动代码）：把页面说明写清楚——16GB 内存机器上"能起服务"不等于"能加载模型"。
- **最低配置结论（必须给用户的那句）**：内存 16GB 的机器在当前实现下**不保证能完成一次模型加载**；要么走路 A/B 把峰值压到 20GB 以内（需实测），要么明确写"建议 32GB 内存"。只靠"少开几个程序"的建议不算数。

**O6 · 明确不要做的三项（写下来防止被再次"优化"回来）**
`torch.compile`（同类项目实测慢 5 倍 + 3 分钟编译）、flash-attn（8GB 卡上显存溢出换页，实测 -95%）、`cudnn.benchmark=True`（变长音频输入，实测 BigVGAN 3.35s→97s）。这三项在这台机器上是负优化，任何"看起来高级"的加速开关都应先用 O2 的剖面证伪。

### 4.2 健壮性

- **O7 · 磁盘余量预检**：生成前检查 `outputs/` 所在盘剩余空间是否够 `目标秒数 × 每秒字节数`，不够就 4xx 提示，而不是让 worker 写到一半 `OSError`（B1 之后这种情况只是不再打死进程，但仍然浪费一次完整生成）。代价：多一次 `shutil.disk_usage`（本地 ~0.1ms）。
- **O8 · 用显式标记替代 `--stop` 的孤儿启发式**（对应 §3.1）：服务进程拉起 worker 时在 `logs/` 写 `worker.pids`（pid + 启动时间 + 端口），`--stop` 只杀登记过且启动时间吻合的 PID。代价：文件可能陈旧（进程崩溃没来得及清），所以要"登记 + 进程仍存活 + 命令行仍含 spawn_main"三重判定，并且**只有三重都过才杀**——比现在宽泛的匹配更保守，不会漏杀自己人，也不会误杀别人。
- **O9 · `/api/log/client` 之外还缺"客户端可写端点"的统一约定**：目前该端点已有每分钟 60 条预算 + 10s 去重 + 64KB body 上限（`app.py:1663-1665`）。若以后再加"前端可 POST 的端点"，应把这套预算复用一个中间件，而不是各处手写。

### 4.3 前端体验（不改变接口契约的前提下）

- **O10 · 结果卡给出分段时长表**：现在只有总时长和一个偏差角标。`segment_plan` 已经在 health/结果里回传，展开成每段"目标 vs 实际"就能让用户自己看出是哪一段塌了。代价：多一点 DOM，无新接口。
- **O11 · 轮询减负**：页面每 0.5s 打 `/api/health`（一次要跑 nvidia-smi + psutil）。可以拆一个 `/api/status/light`（只回 busy/progress/loaded，不碰驱动），资源条用慢得多的频率单独拉。代价：多一个端点、前端两套节奏；**收益是生成期间页面抖动**（这是 B5 的姊妹问题，B5 只治了探针放大，没治轮询本身）。
- **O12 · 生成排队**：现在 GPU 一把锁，忙时前端直接拦（F2 也让模型操作让路）。给"排队 + 位置显示"要动后端任务表，属于功能而非修复；如果做，务必保持"取消只取消自己的任务"。

### 4.4 工程与测试

- **O13 · 把纯规则抽成 torch-free 模块**（`backend/rules.py`）：`_parse_range` / `_require_finite` / `_build_segments` / `_spoken_duration` 那类估算函数 / 上传文件名正则，都可以脱离 torch 单测。这次 B3/B4/B7/nan 四条都是**纯函数边界**问题，本可以在秒级单测里被抓住。代价：一次搬家 + 保持导入方向（rules 不得 import torch）。
- **O14 · 端到端冒烟脚本**：在备用端口起实例（独占 `AUK_LOG_DIR`）→ 断言 `/api/health` 字段集合（这次能保证"契约没变"，靠的是手写断言，应该固化）→ 加载模型 → 生成 1 段 → 校验输出文件名与时长 → `run.py --stop` 并确认端口释放。这是唯一能挡住"改完后端忘了重启 / 改了字段没告诉页面"的机制。
- **O15 · 前端语法自检**：`index.html` 是单文件（这是刻意的，别拆），但可以在提交前跑一次 `node --check`（把 `<script>` 抽出来）——本轮就出现过一次 Edit 后语法不通过、靠浏览器才暴露。

### 4.5 安全

- **O16 · 非回环监听时要求 token**：服务默认 127.0.0.1（`run.py:327`），但 `AUK_HOST=0.0.0.0` 就能整局域网可访问，而服务**无鉴权且有删除端点**。建议：检测到非回环 host 且没有 `AUK_TOKEN` 时启动即失败并解释原因，加 token 后写进 health 之外的每个端点。代价：局域网共用的用户要多配一个变量（也正因为这样不能默认开）。
- **O17 · 上传只做扩展名白名单，不做内容校验**（`app.py:1281-1284`：后缀必须在 6 个白名单里、落盘名是 uuid + 白名单后缀，读取侧 `_UPLOAD_NAME_RE` 严格匹配 → **路径穿越已经堵死**）。可以再进一步：真正解码一次确认是音频。代价：给上传加一次完整解码时间，而且 m4a/webm 在 ffmpeg 缺席时本来就读不出来（B3 处理的正是这种情况），会误伤能用的文件——所以这条**建议只做警告不做拒绝**。

| 批次 | 内容 | 为什么这个顺序 | 验收 |

| C | **O7 磁盘预检** + **O8 worker 登记** | 都是小改动，直接消掉两类"事后才知道"的失败 | 预检用 1KB 剩余空间模拟；O8 用假 PID 验证三重判定 |
